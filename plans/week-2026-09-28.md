**2026-09-28, from the whole-codebase security audit: one fix, one for
Adam.**
- **Fixed, v0.10.46 (native): the hot channel only moves forward, and
  only to the bundle its signature names.** `frontend.json` is unsigned;
  only the bundle is. So someone able to edit a GitHub release, but without
  the signing key, could have pointed every install at an older signed
  bundle under any version label (a rollback, or a rename past its own
  quarantine). The v0.9.79 audit's F8 flagged it at LOW; v0.10.38 fixed the
  path-traversal half and left this one. Now the signature's trusted
  comment (which minisign's global signature authenticates) must name
  `frontend-<version>.tar.gz`, and the version must be newer than what is
  serving and what is staged. Tested against real Ed25519 signatures made
  for the test; a mutation with the name check off fails.
  `credman.rs` no longer builds a slice from a null pointer when a stored
  credential is empty.
- **For Adam: keybox issues a key without checking the payment settled.**
  `handleCheckoutCompleted` (services/keybox/src/server.js) never reads
  `session.payment_status`. Stripe sends `checkout.session.completed`
  before a delayed method (a bank debit, say) settles, with
  `payment_status: "unpaid"`. Whether that can happen depends on which
  payment methods the Payment Links allow, which only the dashboard shows.
  Not changed here, because the fix needs a dashboard step to go with it:
  skip `unpaid` sessions in code AND add `checkout.session.async_payment_succeeded`
  to the webhook's events (and handle it the same way). Doing the code half
  alone would leave a buyer who pays by bank debit with no key at all. If
  the Payment Links only take cards, none of this can happen. And since
  themes are gone from the app, it may simply be time to stop selling.

**2026-09-28, from the whole-codebase security audit: one fix, one for
Adam.**
- **Fixed, v0.10.46 (native): the hot channel only moves forward, and
  only to the bundle its signature names.** `frontend.json` is unsigned;
  only the bundle is. So someone able to edit a GitHub release, but without
  the signing key, could have pointed every install at an older signed
  bundle under any version label (a rollback, or a rename past its own
  quarantine). The v0.9.79 audit's F8 flagged it at LOW; v0.10.38 fixed the
  path-traversal half and left this one. Now the signature's trusted
  comment (which minisign's global signature authenticates) must name
  `frontend-<version>.tar.gz`, and the version must be newer than what is
  serving and what is staged. Tested against real Ed25519 signatures made
  for the test; a mutation with the name check off fails.
  `credman.rs` no longer builds a slice from a null pointer when a stored
  credential is empty.
- **For Adam: keybox issues a key without checking the payment settled.**
  `handleCheckoutCompleted` (services/keybox/src/server.js) never reads
  `session.payment_status`. Stripe sends `checkout.session.completed`
  before a delayed method (a bank debit, say) settles, with
  `payment_status: "unpaid"`. Whether that can happen depends on which
  payment methods the Payment Links allow, which only the dashboard shows.
  Not changed here, because the fix needs a dashboard step to go with it:
  skip `unpaid` sessions in code AND add `checkout.session.async_payment_succeeded`
  to the webhook's events (and handle it the same way). Doing the code half
  alone would leave a buyer who pays by bank debit with no key at all. If
  the Payment Links only take cards, none of this can happen. And since
  themes are gone from the app, it may simply be time to stop selling.

**v0.10.62: the Guide's row step lays out once, not three times.** The
Live auditor measured 61 layouts on a three-row step. The cause was the
pins: each lane's pinned cell had its width written and its title read
straight after, a forced layout per lane, and the pass after every render
did that three times (unpin and re-measure each cell, measure every title,
re-pin and measure again). Now it writes every lane, reads once, and
writes the fades. On the auditor's rig (8,516 channels, 21 lanes pinned)
a step went from 60 to 72 layouts and 4 to 9ms of layout to 18 to 20 and
1.4 to 2.6ms. A pinned title's width is also kept while its text is the
same, so the same lane isn't measured again every time the window moves.
- New harness, `verify-guide-pins`, on a new fake line ("pins": forty
  channels, staggered programme lengths, titles from "News" to far wider
  than a cell). It checks every pinned title fades exactly when its text
  is wider than the pin, every other title exactly when it overflows,
  across a scroll right and back and after row steps, and that a step
  costs under two layouts per pinned lane. The old code reads 3.0 to 3.3
  and fails; this reads 1.1 to 1.3. A mutation that skews the pinned fade
  by 40px fails the fade checks.
- Checked on the way and not a bug: I suspected the cached width was the
  title's box, not its text, which would fade a short title as its pin
  shrank. It isn't: the cell lays its title out at its own width, so the
  box is the text. Measured against the text itself on every pinned lane,
  no mismatches.

**v0.10.63: the card tilt, and it wasn't a taste call after all.** The
worry was that mounting the tilt on first hover would remount the poster
and replay its fade. It doesn't need a remount. The cost is one line of
the library: on mount it reads each card's rect to size the glare, a
forced layout per card while the screen is still being built. The glare
is invisible at rest (opacity 0, the tilt flat), and the library measures
again on every mouseenter, so `ui/Tilt.tsx` skips only the mount's
measure and every tilt in the app uses it. On a 300-card rig: 142 to
227ms and 300 layouts to mount, now 38 to 48ms and none. The window
resize still measures, because Stream's hero fires one after each slide;
that is where a never-hovered card gets its size now, about 20ms per 300

**For you: multi-view's HLS tiles, an architecture call.** Tiles playing
`.m3u8` still fetch the provider directly (`MultiviewTile.tsx`), so a
provider that redirects or sends no CORS header fails them, and the tile
says it can't reach the provider. `.ts` tiles go through the native proxy
since v0.9.101; your panel serves `.ts`, so this only bites M3U lines that
hand out `.m3u8`. Two ways, both native, both about M:
- **The proxy rewrites playlists (my pick).** `mvproxy.rs` serves the
  `.m3u8`, rewrites every URI in it (variants, segments, keys, init
  segments) to point back at itself, and fetches each one the way it
  fetches `.ts` now: redirects followed, the header added. One route for
  every tile, and hls.js doesn't know.
- **An hls.js loader over a native fetch.** Smaller in Rust, but every
  segment of up to four tiles crosses the IPC bridge as bytes, which is the
  cost the proxy was built to avoid.
